Replace link-based password reset with a verification-code flow;
modernize the Settings password section; add a confirmation popup
when Google sign-in links to an existing password account

None of this was covered by prior work - confirmed by reading the
actual forgot-password/reset-password routes and the Google auth
route before starting, not just by scanning recent commit messages.
The old flow was link-only (emailed token -> /reset-password?token=),
which is what the reported "Something went wrong" error was actually
symptomatic of: no verification-code concept, no resend/invalidate,
existed anywhere. The Google account-linking backend logic already
worked correctly (auth_google() has always linked by email) - only
the frontend confirmation message was missing.

server/models/password_reset_code.py                        [A]
    New PasswordResetCode model + CRUD, mirroring
    password_reset_token.py's hashing approach (only a SHA-256 hash of
    the code is ever stored). 6-digit codes, 10-minute TTL (vs. the
    link flow's 1 hour, since this is meant to be entered right after
    the email arrives), 5-attempt cap enforced independently of
    Flask-Limiter's route-level throttle, and a 30-second resend
    cooldown enforced inside create_reset_code() itself so any caller
    gets the same protection. invalidate_active_codes() backs the
    "wrong email, go back" path - abandoning the flow kills the
    outstanding code immediately rather than leaving it valid.

server/migrations/versions/9dd9f4e91099_add_password_reset_codes.py [A]
    Adds the password_reset_codes table. down_revision points at
    635cd82587f6 (add_notifications_table), the actual current head -
    verified with `alembic heads` before writing this, since the local
    app.db's stamped version (7342a5f24b87) had drifted behind the

server/app.py                                                [M]
    - forgot_password(): now creates+sends a 6-digit code instead of a
      token/link. Same email-enumeration protection as before (generic
      response regardless of registration, send failures swallowed
      and logged rather than propagated) - factored the
      create-code-and-send-it logic into a shared
      _send_reset_code_or_none() helper so forgot_password() and the
      new resend route can't drift apart on that protection.
    - New POST /api/auth/forgot-password/resend: invalidates the
      outstanding code and sends a fresh one. Surfaces the resend
      cooldown as a distinct "please wait" message when hit - safe to
      do without leaking account existence, since the same generic
      wording still covers the unregistered-email case.
    - New POST /api/auth/forgot-password/back: invalidates any
      outstanding code for an email. Called when the user leaves the
      verify-code screen to correct their email.
    - New POST /api/auth/forgot-password/verify: checks a guessed code
      against the active one for that email. On a match, logs the user
      in immediately (session cookie, same pattern the old
      reset_password() used) - this is what lets the frontend land
      directly on Profile > Settings to actually change the password,
      fully authenticated, instead of a separate one-off "set new
      password" form. Distinguishes mismatch / expired /
      too-many-attempts for the frontend without leaking whether the
      email itself is registered.
    - reset_password() (token-based): kept as-is, now documented as a
      legacy path only - any reset link already emailed before this
      deploy (1-hour TTL) still redeems correctly. New requests no
      longer generate these tokens/links at all.
    - auth_google(): now tracks whether this sign-in linked Google to
      a pre-existing password account that hadn't used Google before
      (as opposed to a repeat login or a reactivated already-linked
      account), and returns it as a sibling `linked_existing_account`
      key alongside the user fields - not folded into
      to_public_dict() itself, since that shape is shared by every
      auth/profile endpoint and this flag only describes what happened
      in this one request.
