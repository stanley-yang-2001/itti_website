Profile page: vertical sidebar nav + working account settings

Profile page restructured around a vertical sidebar (Profile ->
Favorites -> Publications -> Settings) instead of a flat scroll of
sections:
- Removed the Quick Links section and the "Account settings" button
  next to the avatar/name (and their now-dead CSS).
- "Settings" (renamed from "Account settings") is now a tab in this
  same sidebar, backed by a new shared SettingsPanel component also
  used by the standalone /settings route (kept working since
  PrivacyPolicy.jsx links to it directly) - one implementation, not
  two copies to drift apart.

Discovered while building this that account settings didn't actually
work at all: Settings.jsx called useAuth().updateAccount and
.deleteAccount, neither of which existed anywhere, and the UI checked
user.has_password/user.google_linked, neither of which the API
returned. Built the missing stack rather than just wiring up new UI
to it:
- POST /api/auth/update-profile: updates name and/or password.
  Password changes require the correct current_password (verified
  server-side) and a new password meeting the length requirement;
  Google-only accounts (no password_hash) are rejected with a clear
  message instead of a confusing failure.
- POST /api/auth/update-picture + GET /api/users/<id>/picture: profile
  picture upload/serving, reusing the same storage abstraction
  (server/storage.py) reports already use. New picture_path/
  picture_mime_type columns (migration b7e3f9a1c2d4) keep an uploaded
  picture's internal storage path separate from picture_url (which
  stays the public-facing value the frontend reads directly, whether
  that's our own serving route or an external Google avatar URL).
- User.to_public_dict() now includes has_password and google_linked.
- AuthContext gained updateAccount(fields), updatePicture(file), and
  deleteAccount() to match what the UI was already trying to call.

Every "Confirm" button in the new Settings tab is disabled until its
own section has an actual, validly-formed change pending: picture
(disabled until a file is chosen), username (disabled until it
differs from the current name), password (disabled until current/
new/confirm are all filled in, new/confirm match, and new meets the
length requirement).

Also re-fixed CountryProfiles.css's sticky-nav regression and restored
its narrative-profile overview styles - the third time this same
pattern has reverted on this file from what looks like a stale-branch
merge; flagging for investigation into what keeps reintroducing it.

Verified: clean npm run build; backend smoke tests covering wrong
current password (400), empty name (400), weak new password (400),
unauthenticated requests (401), and a full picture upload -> serve
round-trip.
